# ADR 0001. Arweave — permanent layer; gateway — заменяемый transport

Статус: **принят** (2026-08-20, владелец). Детальная спецификация и разбиение
на PR — `docs/ARWEAVE-RESILIENCE-PLAN.md` (v13, 10 раундов ревью +
интегрированная security-ревизия контура). Этот ADR фиксирует решения и
инварианты; при расхождении нормативен план.

## Контекст

Постоянное хранение (Arweave) и постоянный доступ (gateway) — разные
свойства. Сегодня ВЕСЬ доступ приложения жёстко завязан на единственный
`arweave.net`: проба доступности, статус транзакций, GraphQL-поиск при
restore, скачивание payload, серверные anchor/price/post и перепроверка
статуса, CSP `connect-src` (точные места — §1 плана). Отказ или деградация
одного шлюза — это недоступность и чтения, и записи, а дефекты семантики
статусов (одиночный `404` → `dropped` на клиенте; `404` И `400` → `dead` в
Worker) способны спровоцировать лишнюю платную публикацию.

Инкрементальный sweep (PR #53) уже принял модель недоверия одному индексу
(сознательный отказ от block-height cursor). Данный ADR — прямое продолжение
той же логики на весь транспортный слой.

## Решение

Arweave трактуется как постоянный слой хранения; конкретный gateway — как
заменяемый транспорт без собственного доверия. Зафиксированные решения:

- **D1.** Список шлюзов — build-time (как `VITE_TRUSTED_OWNERS`); смена =
  релиз. CSP `connect-src` строится только из утверждённых origin.
- **D2.** Multi-index restore — всегда параллельно. **Privacy trade-off
  (осознанный):** метаданные активности (Owner-Hash, число транзакций, IP)
  видят ВСЕ операторы настроенных шлюзов, а не один. Принято, потому что
  содержимое зашифровано (AES-GCM), а риск умалчивания одним индексом
  считается весомее расширения круга наблюдателей метаданных. Формулировка
  эффекта — «снижает риск single-index omission», НЕ «закрывает умалчивание».
- **D3.** Strict verification (data_root/Wayfinder) — «защита в глубину», вне
  этого трека: инварианты конверта (см. ниже) уже исключают подмену payload.
- **D4/D5.** Метрики: серверная телеметрия ТОЛЬКО (Workers Analytics Engine,
  Free-план подтверждён); доступ — `/admin/metrics` (bearer) + SQL API.
  Клиентской телеметрии нет.
- **D6.** `restore.html` хранится на Arweave и распространяется как
  СКАЧИВАЕМЫЙ ФАЙЛ с проверкой SHA-256 доверенным агентом — не как
  исполняемая gateway-страница.
- **D7.** Состав шлюзов утверждён по живым пробам (19–20.08.2026):
  status — arweave.net, ar-io.dev, vilenarios.com, frostor.xyz, permagate.io;
  индексы — arweave.net + Goldsky (два независимых) с transport-fallback
  внутри логической группы; payload — arweave.net, vilenarios, ar-io.dev,
  frostor (permagate исключён: холодный `/raw` нестабилен). `UPLOAD_GATEWAYS`
  утверждаются по staging-испытаниям (платные транзакции разрешены).
- **D8.** Типы endpoint различаются: индексы — полные HTTPS URL,
  сгруппированные в логические источники `INDEX_SOURCES` (дедуп по полному
  URL); status/payload/upload — bare origins (дедуп по origin).
- **D9. Верифицируемый payload.** Пул payload-шлюзов допустим ТОЛЬКО вместе с
  проверкой соответствия байтов запрошенному txId. Без неё пул расширяет
  множество тех, кто может подсунуть подлинную, но ДРУГУЮ версию той же
  заметки (она проходит и inner-id, и AES-GCM), то есть ухудшает целостность
  по сравнению с одним шлюзом. Протокол: header `GET /tx/<id>` из того же
  пула → `data_size` → `id = SHA-256(signature)` → RSA-PSS над deep-hash →
  пересчёт `data_root` → **сверка адреса владельца с `TRUSTED_OWNERS`** →
  и только затем JSON/AES-GCM. **Аутентифицированный ≠ доверенный:** без
  предпоследнего шага корректно подписанная транзакция чужого кошелька
  прошла бы всю цепочку. После D9 GraphQL — только дискавери; атрибуция
  берётся из верифицированных тегов.
- **D10. Ограниченность трат.** Автономная (alarm-driven) публикация не
  выпускается без глобального предохранителя горячего кошелька. Учёт — в
  Winston (не в числе публикаций): floor остатка, скользящий бюджет трат,
  потолок стоимости одной транзакции; атомарное резервирование в отдельном
  глобальном DO по ключу `{noteId, generation}` (failover того же tx не
  списывает дважды, redrop = новая generation = новая резервация);
  неизвестный исход POST трактуется как трата; баланс и цена берутся
  медианой по ≥2 шлюзам (минимум дал бы одному лгуну остановить сервис,
  максимум — открыть слив); недоступность источников или DO → fail-closed.
- **D11. Наблюдаемость умалчивания.** Расхождение индексов о наличии txId
  всегда даёт метрику; `incomplete` поднимается только при ДОКАЗУЕМОЙ
  давности, а доказательство берётся из кворума статусов, а не из
  метаданных оцениваемого индекса. Недоказуемый возраст не поднимает
  пользовательский сигнал.

### Инварианты (нормативные)

1. **same-signed-tx / generation:** write-path НЕ создаёт второй
   DURABLE/POSTABLE txId без доказанного кворумом `dead` (строгий N-of-N по
   всем настроенным status-origin + 30-мин age guard). Failover = повтор
   ТОГО ЖЕ подписанного tx. Новая generation открывается единственным путём
   `signed → redrop_pending`; durable-коммит и POST — только у
   CAS-победителя; эфемерные вызовы signer (конкуренты, crash до CAS)
   допустимы и всегда отбрасываются. Главный security-KPI: новых
   durable/postable txId без подтверждённого dead — ноль.
2. **trust-инвариант restore:** байты `restore.html` проверяются доверенным
   агентом (PWA либо терминальный cold-flow: curl → программная сверка
   SHA-256 → rename только при совпадении) ДО исполнения и до приёма seed.
   MIME/заголовки шлюза защитой не считаются. Холодное восстановление —
   только ПК; мобильный cold-restore без приложения не поддерживается
   (отложенная задача).
3. **Целостность payload:** внутренний id конверта обязан совпадать с
   Note-Id-тегом; «текущая» версия определяется аутентифицированным
   timestamp изнутри AES-GCM-конверта, не данными шлюза. Эти проверки не
   ослабляются ни на одном шлюзе. **Уточнение по security-ревизии:**
   `TRUSTED_OWNERS` — build-time пин, `assertTrustedOwners()` проверяет, что
   он НАСТРОЕН; фильтр `owners:` исполняет шлюз, и клиент сегодня не сверяет
   владельца ребра, поэтому фактический клиентский рубеж — расшифровка и
   inner-id, а не owners-фильтр. Аутентифицированная проверка владельца
   появляется вместе с верификацией `txId ↔ bytes` (D9).
4. **Семантика статусов:** `dead` ⟺ КАЖДЫЙ настроенный status-origin ответил
   `404` и настроено ≥2; любой иной исход любого origin (timeout, `4xx/5xx`,
   malformed) делает вердикт `unavailable`. `400` никогда не `dead`.
   Production build fail-closed: `MIN_STATUS_ORIGINS = 2`.
5. **Верифицируемость транспорта (D9):** пул payload-шлюзов допустим ТОЛЬКО
   с проверкой соответствия байтов запрошенному txId — иначе он расширяет
   множество тех, кто может подсунуть подлинную, но ДРУГУЮ версию заметки
   (она проходит и inner-id, и AES-GCM). Верификация даёт заодно
   аутентифицированного владельца.
6. **Ограниченность трат (D10):** автономная (alarm-driven) публикация не
   выпускается без глобального предохранителя горячего кошелька — порога
   баланса, общего бюджета публикаций и аларма скорости сжигания.
   Существующие лимиты поштучные (per-key/per-IP) и агрегат не ограничивают.

### Остаточная Byzantine-модель полноты

Multi-index защищает от подмены и от умалчивания ОДНИМ индексом. Он НЕ
доказывает глобальную полноту: все настроенные индексы могут отставать или
согласованно умалчивать. `incomplete=false` означает строго «все настроенные
ЛОГИЧЕСКИЕ источники дочитаны до конца», а не «на chain больше ничего нет».

### Failure domains (оговорка независимости)

Операторы пяти status-шлюзов различны, но программная реализация у всех —
ar.io-стек (включая сам arweave.net): один software failure domain, общий баг
затронет всех одновременно. Независимых индексных РЕАЛИЗАЦИЙ две — arweave.net
и Goldsky; GraphQL ar.io-шлюзов — транспортная избыточность того же индекса,
не второе мнение. Именно поэтому dead-формула — строгий N-of-N, а ослабление
до K-of-N допустимо только отдельным ADR со счётом голосов по независимым
failure domains (софт + оператор), а не по числу origin.

## Не делаем (с условиями пересмотра)

- **bundles/ANS-104** — до изменения масштаба записей на порядки;
- **AO/HyperBEAM/Solana/ArNS** — не входят в цепочку восстановления; пересмотр
  только при появлении собственной ценности, не «за компанию»;
- **Wayfinder SDK в PWA-бандл** — до появления бюджета и доказанной нужды
  (строгая верификация уже покрыта инвариантом 3);
- **клиентская телеметрия** — D5; пересмотр только явным решением владельца;
- **мобильный cold-restore verifier** — отложен в бэклог (решение владельца
  2026-08-19); основной мобильный путь — восстановление через PWA;
- **подписанный high-water mark** (Worker аттестует «не меньше N txId / не
  ниже ревизии V») — отдельный ADR; единственная защита от downgrade на
  чистом устройстве, но живёт ровно столько, сколько Worker, поэтому НЕ
  входит в автономный `restore.html` и не имеет права вернуть height-курсор.
  Пересмотр — по метрике расхождений индексов (§ плана 2, D11).

## Последствия

- Read-path (статусы, payload, индексы) перестаёт зависеть от одного шлюза;
  цена — расширенный CSP и метаданные у большего числа операторов (D2).
- Write-path получает строгий протокол signed/redrop_pending с
  reader-before-writer раскаткой и hard rollback floor (`docs/ROLLBACK.md`).
- Один флапающий status-шлюз откладывает `dead` — осознанная безопасная
  сторона: `unavailable` денег не тратит.
- Порядок работ утверждён: метрики → read-path multi-gateway → multi-index →
  автотриггеры sweep → write-path failover → restore.html.
