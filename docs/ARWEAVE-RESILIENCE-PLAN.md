# План: устойчивость доступа к Arweave (multi-gateway, метрики, restore.html)

Статус: на ревью. Дата: 2026-08-18.

Основание: анализ «Arweave: изменения апреля–августа 2026» + сверка с кодом.
Документ адресован ревьюеру: фиксирует принятые решения, объём работ,
разбиение на PR, тестовые сценарии и границы (что сознательно НЕ делаем).

---

## 1. Контекст: проверенные факты

Постоянное хранение (Arweave) и постоянный доступ (gateway) — разные свойства.
Сегодня доступ жёстко завязан на единственный `arweave.net`:

| Место | Файл | Что делает |
|---|---|---|
| Клиент | `src/lib/arweave.ts:207` | проба доступности `/info` |
| Клиент | `src/lib/arweave.ts:242` | статус транзакции `/tx/{id}/status` |
| Клиент | `src/lib/arweave.ts:513` | GraphQL-поиск при restore |
| Клиент | `src/lib/arweave.ts:677` | payload `/raw/{txId}` |
| Worker | `worker/src/index.ts:144, 747` | `Arweave.init` (anchor+price+post) |
| Worker | `worker/src/index.ts:933` | серверная перепроверка статуса |
| CSP | `scripts/postbuild.mjs:39` | `connect-src` пинит только `arweave.net` + proxy |

Ключевые дефекты семантики статусов:

- клиент: одиночный `404` → `dropped` (`src/lib/arweave.ts:247`);
- Worker: `404` **и `400`** → `dead` (`worker/src/index.ts:938`) — `400` от
  деградировавшего шлюза на валидный txId через 30-минутный age guard ведёт к
  redrop и повторной оплате;
- клиентская и серверная проверки бьют в один хост — они коррелированы,
  отставание индекса `arweave.net` дольше 30 минут даёт ложный `dead`.

Что УЖЕ защищено кодом (проверено, менять не нужно):

- подмена payload между версиями невозможна: внутренний `id` конверта обязан
  совпадать с Note-Id-тегом (`src/lib/arweave.ts:795–803`), каждая версия
  имеет собственный uuid;
- «текущая» версия выбирается по аутентифицированному timestamp ИЗНУТРИ
  AES-GCM-конверта (`src/lib/chains.ts`, `byCurrentness`), а не по данным шлюза;
- восстановление fail-closed по `VITE_TRUSTED_OWNERS` (`src/lib/config.ts`).

Остаточная атака нечестного индекса — умалчивание (не показать новейшую
версию). Её закрывает multi-index union (решение D2), а не проверка data_root.

## 2. Зафиксированные решения

- **D1. Список шлюзов — build-time.** Задаётся при сборке, как
  `VITE_TRUSTED_OWNERS`; смена списка = релиз. Совместимо со строгой CSP.
- **D2. Multi-index restore — всегда параллельно.** Каждый restore опрашивает
  все индексы и объединяет результат. Осознанная цена: метаданные активности
  (Owner-Hash, число транзакций, IP) видят все операторы шлюзов из списка.
- **D3. Strict verification (data_root/Wayfinder) — понижена до «защиты в
  глубину»** на основании инвариантов «inner id = tag» и «currentness из
  аутентифицированного envelope». Не входит в этот план.
- **D4. Доступ к метрикам: `/admin/metrics` (bearer `ADMIN_SECRET`) + прямой
  Cloudflare Analytics Engine SQL API** для глубоких запросов.
- **D5. Телеметрия — только серверная.** Клиент ничего не отправляет; метрики
  собирает только Worker.
- **D6. `restore.html` хранится на самом Arweave**, его txId публикуется в
  README и в приложении.
- **D7. Конкретные адреса шлюзов утверждаются в PR** (кандидаты: публичный
  шлюз ar.io, Goldsky GraphQL) — по результатам замеров, см. PR-3.

## 3. Объём и границы

В объёме: 3 решения (gateway-конфигурация, multi-index, ADR) и 2 задачи
(метрики, restore.html), включая исправление семантики `404/400`.

Сознательно ВНЕ объёма (отдельные ADR, не блокируют этот план):

- перепроектирование сохранения подписанной транзакции ДО публикации
  (устраняет последний сценарий дубля при потере HTTP-ответа POST;
  учесть срок жизни anchor ~50 блоков);
- bundles/ANS-104 — вопрос закрыт до изменения масштаба на порядки
  (стоимость версии заметки ~сотые доли цента);
- AO/HyperBEAM/Solana/ArNS — не входят в цепочку восстановления;
- Wayfinder SDK — не тащим в PWA-бандл; собственный пул из 2–3 шлюзов
  дешевле и без вопросов к CSP;
- клиентская телеметрия (D5) и инкрементальный sweep (отдельный трек).

### PR-2 «Метрики» (до любых multi-gateway работ — иначе эффект нечем измерить)

**Worker, Analytics Engine:**

- `worker/wrangler.toml`: биндинг
  `[[analytics_engine_datasets]] binding = "METRICS"` (+ dataset name).
- Инструментация (новый модуль `worker/src/metrics.ts`, вызовы из
  `worker/src/index.ts`):
  - `gateway_call`: endpoint-тип (`status|anchor|price|post`), хост, класс
    HTTP-статуса (`2xx|4xx|404|429|5xx|timeout`), latency ms;
  - `upload_outcome`: `accepted_committed | accepted_uncommitted |
    recovery_token_issued | rate_limited | in_progress | gateway_error |
    reserve_denied`, флаг recheck;
  - `repost`: каждый redrop/re-post (метрика «повторная публикация той же
    версии» — главный индикатор ложных dead);
  - `status_verdict`: alive/dead/unavailable (+ после PR-3 — расхождения
    между шлюзами).
- Запрет на содержимое: ни plaintext, ни seed, ни ключей, ни note content.
  Идентификаторы в метрики не пишем вовсе (при необходимости расследования
  дублей — усечённый SHA-256 от noteId, отдельным решением).
- Запись безусловная и невозможная к падению: обёртка try/catch, отказ
  метрик никогда не влияет на путь запроса.

**Доступ (ответ на вопрос «каким образом доступ к панели»):**

Два независимых ключа, обе стороны уже поддерживаются инфраструктурой:

1. `/admin/metrics?report=<имя>&window=<24h|7d>` — новый GET-эндпоинт под
   существующей constant-time bearer-проверкой `ADMIN_SECRET`
   (`worker/src/index.ts:169–181`). Возвращает JSON-сводку по
   ПРЕДОПРЕДЕЛЁННЫМ отчётам (никакого free-form SQL через Worker):
   `gateways` (доступность/латентность по хостам), `uploads` (исходы),
   `reposts`, `verdicts`. Внутри Worker вызывает Analytics Engine SQL API
   (`api.cloudflare.com`) с секретами `CF_ACCOUNT_ID` и `AE_SQL_TOKEN`
   (API-токен, скоуп только Account Analytics Read).
2. Прямой SQL API для глубоких запросов — готовые команды `curl` и типовые
   запросы документируются в `docs/METRICS.md` (создаётся в этом PR).

Итого «панель» = `curl -H "Authorization: Bearer $ADMIN_SECRET"
https://<worker>/admin/metrics?report=gateways` для ежедневного взгляда,
SQL API — для расследований. Отдельный UI не строим (масштаб не оправдывает);
если понадобится — Grafana поверх того же SQL API, без изменений Worker-а.

**Тесты PR-2:** метрики не ломают happy-path при недоступном биндинге;
`/admin/metrics` без/с неверным токеном → 401/503; отчёты валидируют `report`
и `window` по белому списку.

### PR-3 «Gateway-конфигурация + семантика статусов»

**Клиент:**

- Новый `src/lib/gateways.ts`: типизированная конфигурация из build-time
  переменных `VITE_ARWEAVE_INDEX_GATEWAYS`, `VITE_ARWEAVE_PAYLOAD_GATEWAYS`,
  `VITE_ARWEAVE_STATUS_GATEWAYS` (CSV bare-origin; валидация как у
  `PROXY_URL`, `src/lib/arweave.ts:30–38`; при пустом значении — текущий
  дефолт `https://arweave.net`, поведение не меняется).
- `scripts/postbuild.mjs:39`: `connect-src` собирается из union всех
  gateway-списков + proxy (вместо hardcoded `arweave.net`).
- `isArweaveOnline` → «жив хотя бы один status-шлюз» (параллельно,
  `Promise.any`, прежний таймаут).
- `getTxStatus` → кворум по `statusGateways` (`Promise.allSettled`):
  - хотя бы один `200/202` → `confirmed`/`pending`;
  - `404` от ВСЕХ ответивших при ≥2 ответивших хостах → `dropped`;
  - одиночный `404`, `400`, `429/503`, timeout → `unavailable` (никаких
    действий; `afterPoll` в `src/lib/sync-transitions.ts` уже трактует
    `unavailable` как «ничего не менять»);
  - `invalid` остаётся только для локально-невалидного txId.
- `/raw/{txId}`: перебор `payloadGateways` при сетевой ошибке/не-2xx;
  существующие проверки (inner id = tag, AES-GCM, trusted owners) не
  меняются.

**Worker:**

- `worker/wrangler.toml` `[vars]`: `ARWEAVE_GATEWAYS` (CSV, первый — primary
  для anchor/price/post).
- `getTxStatusWorker` → кворум, те же правила, что на клиенте; `400`
  больше НИКОГДА не `dead`. `dead` требует: ≥2 независимых хоста ответили,
  все — `404`, плюс существующий 30-минутный age guard (не трогаем).
  Бюджет subrequests: ≤3 хостов × ≤2 проверок на запрос — в пределах лимита.
- Upload: anchor/price/post пробуют primary; при ЯВНОМ отказе (получен
  не-2xx ответ) — повтор полного create+sign+post на следующем хосте.
  При timeout POST (исход неизвестен) повтора на другом хосте НЕТ —
  поведение как сегодня (502, reservation released); устранение этого
  сценария — отдельный ADR (см. границы).

**Тесты PR-3** (сценарии раздела 7 отчёта):

- status: `404` на одном хосте + `202` на другом → pending/alive;
- status: `404` на всех при одном ответившем хосте → unavailable (не dead);
- status: `400` от шлюза → unavailable, redrop не запускается;
- `/raw` `404` на первом шлюзе, `200` на втором → нота восстановлена;
- `/info` недоступен на первом, доступен на втором → online;
- пустые env-переменные → поведение идентично текущему (снапшот-тест CSP);
- lock/reset отменяет запросы ко ВСЕМ шлюзам (существующая `requestSignal`
  композиция сигналов покрывает — тест фиксирует).

**Выбор хостов (D7):** в PR приводится замер кандидатов (полнота GraphQL
по реальному ownerHash, латентность, поведение пагинации) и предлагается
итоговый список; утверждение — при ревью PR.

### PR-4 «Multi-index restore»

- `fetchPage` параметризуется origin-ом индекса; пагинация ВНУТРИ индекса
  остаётся последовательной (курсор `after` — opaque и непереносим между
  индексами), индексы опрашиваются параллельно.
- Union кандидатов по `txId` до payload-фазы (без двойных `/raw`).
- Порядок и выбор победителя НЕ меняются: claim после успешной дешифровки,
  currentness — из аутентифицированного конверта (см. раздел 1).
- `incomplete`-семантика (строгая, по отчёту): `incomplete=false` только
  если ВСЕ индексы дочитаны до конца; любой сбой страницы/индекса →
  `incomplete=true`, но union всё равно возвращается.
  Рассмотренная альтернатива («достаточно одного полностью дочитанного
  индекса») отвергнута: полный индекс A не гарантирует наличия транзакций,
  которые знал только отставший B; флаг — про честность обещания.
- `ArweaveIndexUnavailableError` — только когда ПЕРВАЯ страница упала у
  ВСЕХ индексов (и не по abort).
- Backoff/jitter на `429/503` per-index; общая ограниченная параллельность
  payload-фазы сохраняется (`RESTORE_CONCURRENCY`).
- Расхождения индексов логируются в console (метрик с клиента нет — D5).

**Тесты PR-4:**

- первый индекс `503`, второй отдаёт все страницы → полный restore;
- один индекс пуст, второй с данными → данные восстановлены,
  `incomplete=false` (оба дочитаны);
- второй индекс отстаёт на версию → union содержит новейшую,
  победитель детерминирован;
- обрыв пагинации одного индекса → `incomplete=true`, union возвращён;
- падение первой страницы у всех → `ArweaveIndexUnavailableError`;
- неправильный owner / повреждённый конверт отклоняются независимо от того,
  какой индекс принёс кандидата;
- порядок ответов индексов не влияет на победителя цепочки (перестановочный
  тест).

### PR-5 «restore.html на Arweave»

- Отдельная сборка `restore/` → один самодостаточный HTML (все ассеты
  инлайн): криптография v1–v4, `TRUSTED_OWNERS` запинены при сборке,
  gateway-пул из D1 + ручное добавление шлюза, multi-index sweep из PR-4
  (общий код выносится в переиспользуемые модули без DOM-зависимостей).
- **Только память, никакой персистентности.** Страница обслуживается с
  origin шлюза (`https://<gateway>/<txId>`), который ДЕЛИТ storage со всем
  остальным контентом этого шлюза: localStorage/IndexedDB/SW запрещены,
  экспорт расшифрованного — только явным действием пользователя, на
  странице предупреждение «закройте вкладку после использования».
- CSP через `<meta http-equiv>`: `default-src 'none'`, script/style только
  инлайн-хеши, `connect-src https:` — сознательно шире, чем в PWA, иначе
  ручное добавление шлюза невозможно; наружу уходят только ownerHash-запросы
  и запросы payload (шифртекст), seed страницу не покидает. Trade-off
  фиксируется в ADR.
- Публикация: `scripts/publish-restore.mjs` — запускается ЛОКАЛЬНО
  оператором с серверным кошельком (не Worker-ом), тег
  `App-Name: EternalNotesRestore`; после публикации скрипт скачивает файл
  с ≥2 шлюзов и сверяет SHA-256 с локальной сборкой.
- txId публикуется: README (раздел «Аварийное восстановление», история
  версий txId), экран настроек приложения (ссылка + `ar://<txId>`),
  `docs/ROLLBACK.md` (перекрёстная ссылка).
- Acceptance: восстановление работает при полном отключении Matamata
  Worker, Cloudflare и Solana; форматы v1–v4; невалидный owner отклонён.

## 5. Метрики успеха (сравнение до/после по данным PR-2)

- «повторная публикация той же версии» (`repost`) → к нулю;
- доля `status_verdict=dead`, опровергнутых кворумом → видима и падает;
- p95 latency и доля `5xx/timeout` по каждому хосту → основание для D7;
- доля restore c `incomplete=true` — недоступна (D5), прокси-метрика:
  доступность index-эндпоинтов по серверным пробам не вводим сознательно
  (Worker не должен опрашивать GraphQL без нужды) — пересмотр при появлении
  жалоб на частичные восстановления.

## 6. Риски и открытые вопросы к ревью

1. **Хосты D7** — утверждаются в PR-3 по замерам (полнота индекса важнее
   латентности).
2. **Строгая `incomplete`-семантика** может чаще показывать «частичное
   восстановление» при флаки-вторичном индексе. Принимаем как честность;
   альтернатива описана в PR-4 — возражения приветствуются.
3. **`connect-src https:` в restore.html** — шире, чем в PWA; обоснование в
   PR-5, возражение ревьюера = откат к запиненному списку без ручного
   добавления шлюза.
4. **Секреты PR-2**: `AE_SQL_TOKEN` — новый секрет Worker-а; скоуп строго
   Account Analytics Read; ротация независима от остальных.
5. Каждый PR самостоятелен и откатываем; пустые env-значения везде дают
   текущее поведение (fail-safe defaults).
