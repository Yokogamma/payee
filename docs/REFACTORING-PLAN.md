# Аудит границ модулей и план рефакторинга

Дата: 2026-09-14. Статус: предложение для согласования, реализация не начата.

## Цель и границы

Проблема пользователя: крупные модули трудно понимать; изменение одной функции затрагивает соседний код.
Цель — локализовать изменения по предметным областям, сделать зависимости и владение состоянием явными.
Размер файла — индикатор, а не критерий успеха. Перенос функций с передачей им всего прежнего store проблему не решает.

Предлагается сохранить функции, интерфейс, форматы данных, API и поведение блокировки. Новые библиотеки управления состоянием, миграции БД и изменения протокола в этот план не входят.

Аудит основан на чтении структуры, основных функций и существующих тестов. Это архитектурный разбор, не полная проверка безопасности и не доказательство наличия ошибок выполнения. Тесты и профилирование на этапе аудита не запускались. Ссылки ниже относятся к исходному состоянию до рефакторинга.

## Наблюдения по приоритету

### 1. Store объединяет владельцев разных состояний

`src/lib/store.tsx:813`: NotesProvider занимает большую часть файла из 4722 строк. Он совмещает сессию, загрузку приложения, заметки, очередь, restore, PIN, быстрый вход, сейф и браузерный lifecycle.

Особенно показательные места:

- `:1559` — invalidateVaultLifecycle меняет поколения сессии и очереди, блокирует сейф, отменяет операции открытия и быстрого входа.
- `:1931` — clearVaultState знает детали ключей, сейфа, заметок, восстановления, очереди и черновика.
- `:1987` — lockApp задаёт синхронный порядок остановки, очистки, смены экрана и оповещения вкладок.
- `:2991`, `:3365`, `:3594`, `:4114` — действия заметок, PIN, быстрого входа и сейфа живут в одном замыкании.

Следствие: при добавлении состояния разработчик должен найти все пути его публикации, отмены и очистки внутри общего модуля. Компилятор не выражает принадлежность этого состояния подсистеме.

Решение: отдельные владельцы состояния с узкими командами; координацию общей блокировки оставить явной и синхронной. Не заменять её асинхронной шиной событий или независимыми React effects.

### 2. Общий контекст связывает всех потребителей

`src/lib/store.tsx:437` описывает общий NotesStore; `:4556` собирает единое значение контекста, `:4718` возвращает его через useNotes.
Поиск, прогресс restore, PIN и сейф обновляют один контекст. Это расширяет область уведомлений и поверхность зависимостей UI. Измерений задержек нет; заявлять подтверждённую проблему производительности нельзя.

Решение: после выделения владельцев состояния разделить контексты сессии, заметок, sync/restore и сейфа. Узкий hook поверх прежнего useNotes сам по себе не изолирует подписки. Временный совместимый фасад допустим на время миграции потребителей.

### 3. Главный экран совмещает представление и несколько жизненных циклов

`src/screens/Main.tsx:45`, 1416 строк. Компонент одновременно управляет адресом, удержанием выбранной версии, модальными окнами, фокусом, черновиком и PWA.
Примеры: `:152` — фиксация версии; `:257` — подписка PWA; `:593` — загрузка черновика; `:609` — его сохранение; `:617` — сохранение заметки.

Решение: выделить состояние страницы чтения, управление черновиком, взаимодействия редактора и PWA-уведомление. Связанные route, version pin и канонизацию держать вместе. Не распределять их эффекты по несогласованным компонентам.

### 4. Worker смешивает HTTP и публикацию

`worker/src/index.ts`, 1867 строк; handleUpload начинается на `:704`, раздел helpers — на `:1414`.
Обработчик объединяет конфигурацию, авторизацию, версионную валидацию, идемпотентность, резервирование, подпись, отправку, recovery и метрики.

Решение: тонкий router, отдельные handlers, проверка upload-запроса и координатор публикации. Координатор сохраняет видимую последовательность необратимых операций. Ошибки валидации должны сохранять текущие HTTP-коды и тела ответов.

### 5. Storage и crypto требуют предметных границ

`src/lib/storage.ts`, 1708 строк: подключение/миграции БД, заметки, сейф, sync, идентичность хранилища, PIN и quick unlock.
Атомарные операции уже есть: saveNoteWithSync (`:293`), commitSafeboxEntry (`:466`), beginUploadUnlessTerminal (`:754`). Их нужно сохранить целиком.

`src/lib/crypto.ts`, 1209 строк: ключи и подписи, конверты заметок, конверты сейфа, вложения и PIN. Типы NoteData (`:84`) и SafeboxEntryData (`:569`) также находятся здесь.

Решение: разделить подключение БД и предметные операции; выделить типы данных, ключи/подписи, конверты заметок, конверты сейфа и PIN. Сохранить атомарность операций над несколькими stores и точное кодирование аутентифицируемых данных. Универсальный CRUD-репозиторий здесь скроет важные ограничения.

### 6. Вторичные кандидаты

- `src/lib/arweave.ts`, 1274 строки: API регистрации/загрузки, статусы, capabilities, GraphQL-обход и проверка восстановленных записей. Разделять API proxy, опрос статусов и restore transport; существующую проверку доверенных владельцев и tx не дублировать.
- `src/screens/SettingsSection.tsx`, 1014 строк: уже есть отдельные компоненты секций (`:537`, `:655`, `:773`, `:912`, `:951`). Перенос даст удобную навигацию, но сам по себе не устранит связанность store.
- `src/index.css`, 3005 строк: разделение возможно по существующим областям с сохранением порядка каскада. Низкий приоритет относительно состояния приложения.
- `worker/src/index.ts:16` импортирует чистые общие функции из клиентской папки. Позже можно перенести их в нейтральный shared-каталог, сохранив единственную реализацию. Это организационная зависимость, не подтверждённый runtime-дефект.

## Предлагаемые владельцы и зависимости

Названия будущих модулей предварительные; внутренние пути уточняются на соответствующем шаге.

| Область | Чем владеет | Разрешённое взаимодействие |
| --- | --- | --- |
| Session/lifecycle | Идентичность сессии, ключи, epoch, открытие/блокировка, privacy gate, события вкладок | Явно останавливает подсистемы в установленном порядке; выдаёт ограниченный контекст операции |
| Notes | Список заметок, версии, публикация изменений, защита конкурентного редактирования | Storage, crypto, проверка актуальности сессии, команда постановки в очередь |
| Sync | Очередь, её поколение, обработчик, polling, паузы и статусы | Upload-flow, transport, атомарные storage-операции; без доступа к UI PIN |
| Restore | Запуск sweep, прогресс, результат, координация merge | Проверенный transport, атомарный merge, публикация через владельцев заметок/сейфа |
| Access | PIN и quick-unlock операции, их отмена и конфигурация | Session commit, storage, crypto; без управления массивом заметок и очередью |
| Safebox | Секция, её epoch, ключи секции, записи, таймер и действия секретов | Родительская сессия, storage, crypto, очередь; явная синхронная блокировка |
| Main/UI | Маршрут, выбор версии, редактор, фокус, модальные окна | Узкие данные и команды предметных областей |

Session epoch, safebox epoch, queue generation и DB generation имеют разные назначения. Не объединять их в один счётчик. DB generation и проверка непосредственно перед созданием транзакции остаются ответственностью storage.
Не передавать всем модулям весь NotesStore, набор всех refs или неограниченный доступ к ключам. Общий provider после миграции должен собирать подсистемы, а не повторять их алгоритмы.

## Последовательность небольших изменений

Каждый пункт — отдельная проверяемая порция; сложные пункты делятся по одному владельцу состояния. Между переносом кода и изменением поведения не должно быть смешанных шагов.

1. **Зафиксировать исходное состояние.** Выполнить quality gates, записать существующие сбои отдельно. Составить таблицу событий lock/reset/hidden/pagehide/pageshow/config и затрагиваемых операций по текущему коду. Уточнить реальные зависимости первого извлекаемого модуля. Не менять незакоммиченные пользовательские файлы.
2. **Пилот на Main.** Извлечь управление черновиком вместе с dirty guard, debounce и очисткой после save; затем отдельным шагом состояние reader route/version pin и его канонизацию. Разнести UI чтения, списка и PWA. Сохранить фокус, обработку Back и поведение при sweep. Секции настроек переносить отдельно по мере необходимости.
3. **Сократить store через очередь.** Использовать существующий upload-flow.ts, выделить владельца очереди и её остановки. Сохранить текущие проверки epoch/DB generation, единственного работающего processor и правила пауз. Provider передаёт конкретные зависимости и координирует остановку, а не получает доступ к внутренним refs очереди.
4. **Выделить notes и restore.** Переносить по очереди, сохраняя общий запрет конкурирующих sweep и атомарный merge. Публикация заметок должна синхронно согласовывать state/ref, как сейчас. Отдельно определить владельца набора undecryptableIds: он общий для ремонта заметок и сейфа и очищается с сессией.
5. **Выделить safebox, затем access.** Перенести состояние и очистку секции вместе. Сохранить очистку секретных DOM-полей, включая формы настроек вне секции. Затем выделить PIN/quick unlock с собственными механизмами отмены. Session/lifecycle остаётся явным координатором; порядок lock/reset проверяется на каждом переносе.
6. **Разделить контексты.** Перевести потребителей на соответствующие области и удалить временные широкие зависимости. Проверить, что изменение поиска заметок не обновляет контекст сейфа. Не оценивать этот шаг только по уменьшению файла store.
7. **Worker отдельным циклом.** Сначала вынести HTTP helpers и независимые routes, затем upload validation и координатор публикации. Перед каждым переносом сверить порядок kill switches, лимитов, авторизации, подписания, POST и фиксации recovery. Сохранить экспортируемые Durable Object классы и привязки.
8. **Storage/crypto/transport.** Переносить целые операции с сохранением временных экспортов для потребителей. Проверить отсутствие циклов импорта и единственного дублирующегося DB singleton. Изменение файлов storage требует обновления архитектурного теста inventory с сохранением запрета произвольных sync-writers.
9. **CSS и документация.** По необходимости разделить стили с сохранением каскада; обновить карту владельцев и удалить временные фасады после миграции всех потребителей.

## Проверки и критерии приёмки

Существующие опоры: store.test.tsx и специализированные store.*.test.*, Main.test.tsx/Main.v3.test.tsx, upload-flow*.test.ts, storage*.test.ts, sync-transitions.test.ts, restore-quarantine.integration.test.ts; в Worker — routes, upload validation, v3/v4 gates, recheck, revoke и e2e-repost.

Проверить покрытие реальных границ, добавить недостающие сценарии при извлечении:

- lock/reset во время сохранения, restore, отправки, PIN и quick-unlock; поздний результат не публикует данные закрытой сессии;
- события другой вкладки и BFCache; privacy gate и синхронная очистка не откладываются до React effect;
- блокировка сейфа во время reveal/copy/download, очистка полей и отмена старого состояния;
- терминальный карантин, паузы версий, повторная отправка после потери ответа, сохранение txId/recovery;
- черновик не перезаписывает свежий ввод, маршрут версии не меняет читаемый текст при поступлении старых версий;
- чтение старых форматов и работа при выключенных writers/quick-unlock, в том числе после rollback.

Обязательные gates проекта: `npm run lint`, `npm test`, `npm run build` с требуемыми production env; `npm --prefix worker run typecheck`, `npm --prefix worker test`. Node — поддерживаемая проектом линия 24 LTS. Во время локальных шагов запускать соответствующие suites; перед завершением согласованного этапа — обязательные gates. Значения секретов не выводить в отчёты.

`src/lib/sync-writers-inventory.test.ts` привязан к текущему storage.ts; при переносе обновить список разрешённых владельцев, не удалять защиту. `src/index.cascade.test.ts` читает один index.css; при разделении стилей тест должен читать реальный порядок импортов и проверять итоговый каскад.

Готовность этапа: у извлечённой области один владелец состояния; зависимости перечислены явно; нет импорта обратно в общий provider; типичное локальное изменение проверяется тестом области без настройки соседних подсистем. Интеграционные проверки жизненного цикла при этом сохраняются. Новые файлы, скрывающие прежнее общее замыкание за огромным объектом зависимостей, не считаются достижением цели.

Релиз не является частью аудита. Реализация должна сохранять порядок развёртывания и отката из docs/ROLLBACK.md; изменение форматов или удаление старых readers требует отдельного решения.

## Решение для согласования

Рекомендуемый первый этап реализации: исходные проверки, пилот Main и выделение очереди из store. Он затрагивает главную боль и позволяет проверить подход до переноса PIN и жизненного цикла всей сессии. Сохранение функций и совместимости — предлагаемое допущение. Реализация начинается после согласования пользователем.
